# Phase-3A-Q5A Purpose-5 signer genesis candidate v1

## Result boundary

Q4 completed a strict unsigned quotient-certificate body and capability receipt.
It did not install Purpose-5 keys, pin a trust genesis, resolve a current key
status, sign a certificate, or issue an envelope.  Q5A is the next bounded
stage: it may generate three fresh Purpose-5 Ed25519 keys and publish only an
**unpinned public genesis/status candidate**.

The Q5A success state is exactly:

```text
Q5A_PURPOSE5_SIGNER_GENESIS_CANDIDATE_COMPLETE_NOT_PINNED_NOT_SIGNED
```

It is not a trusted/current key status and is not certificate issuance.

## Why pinning is separate

The three keys are generated by an OS CSPRNG after authorization consumption,
so their public keys and resulting genesis root do not exist when the Q5A
capsule is authorized.  An exact owner pin cannot bind a root that is still
unknown.  Consequently:

1. Q5A generates and seals the candidate roots;
2. Q5B uses a new capsule and zero-keygen amendment that binds those exact roots
   and explicitly pins the genesis/current epoch;
3. Q6 uses another capsule for the three signing actions and issuance.

This is an authority boundary rather than a retry workaround.

## Frozen predecessor

The controller replays the exact Q4 capsule, authorization, consumption,
capability artifact and terminal.  Those five objects are the authority chain.
It also replays the three-row Q4 trajectory as audit evidence and requires the
event sequence:

```text
CAPSULE_PREPARED_NOT_AUTHORIZED
AUTHORIZATION_RECORDED_NOT_CONSUMED
Q4_CAPABILITY_ADMISSION_COMPLETE_NOT_ISSUED
```

Every Q4 trajectory action-audit field must remain zero.  The trajectory is
audit input, not a replacement authority object.

## Purpose-5 signer registry

All three keys have `purpose_id = 5`, `key_epoch = 1`, and distinct signer
roles:

| ordinal | signer role |
|---:|---|
| 1 | `FINAL_CERTIFICATE_CUSTODIAN` |
| 2 | `FINAL_CERTIFICATE_PYTHON_REPLAY_ATTESTER` |
| 3 | `FINAL_CERTIFICATE_RUST_REPLAY_ATTESTER` |

Each key is a fresh Ed25519 key.  Its key ID is the first 16 bytes of
`SHA256(raw_public_key_32_bytes)`.  Key IDs and raw public keys must both be
pairwise distinct.  Purpose 1–4 keys, repository test keys and legacy
`phase3_certificate_v1` records are not eligible.

The strict numeric-array CBOR layer publishes:

- three `Purpose5SignerManifestV1` objects;
- one `UnpinnedTrustGenesisCandidateV1`;
- one `GenesisOnlyStatusCandidateV1`;
- one aggregate `Q5aPurpose5SignerGenesisCandidateV1` receipt.

The aggregate binds the complete Q4 authority identity, the Q4 quotient body
hash, Q4/Q5 source identities, the three manifest roots, the genesis candidate
root and the status candidate root.  It reports three candidate signers and
zero active trusted signers, zero signatures and zero issued envelopes.

## Key-bearing worker boundary

Engineering freeze, capsule preparation, startup smoke and tests never generate
or access a private key.  Actual key generation is reachable only after exact
Q5A authorization consumption.

The actual campaign invokes three strictly ordered worker actions.  Each action:

1. receives one fixed signer ordinal/role and UID/GID;
2. creates a fresh, repository-external custody root with mode `0700`;
3. invokes `/usr/bin/openssl genpkey -algorithm ED25519` once;
4. stores only `ed25519-private.pem` in that custody root with mode `0600`;
5. reloads the private key through OpenSSL and exports only the public SPKI;
6. verifies the exact Ed25519 SPKI prefix and extracts the 32-byte public key;
7. writes a public receipt and public DER outside the custody root;
8. reports `private_key_exported=false`, `signature_count=0` and
   `key_generation_count=1`.

The controller never opens or reads the private-key file.  Successful Q5A
completion deliberately retains all three custody roots for a separately
authorized Q6; it does not clean them up.

## State and continuation

Before consumption, local Q4 replay, source, interpreter, OpenSSL/path,
permission or fresh-root admission failures may enter same-capsule `PENDING`
with authorization consumption, campaign and key-generation counts all zero.

After consumption, acquisition of the next signer is permitted only from clean
completed prefixes `[]`, `[1]`, or `[1,2]`.  The complete public-result prefix
`[1,2,3]` may enter `PENDING` only while deterministically finalizing its public
wrapper, checkpoint, trajectory suffix or candidate-artifact publication; it
can never invoke another worker.  Before each worker Popen the controller
durably writes that signer's intent.  A completed signer is never invoked
again.  An unknown
post-intent outcome, an invalid public receipt, inability to prove public/private
correspondence through the worker result, or any state contradiction is
terminal no-resume.  Once the public candidate artifact is sealed, only exact
artifact-to-terminal partial finalization remains.  If a terminal is already
durable but its final trajectory row is not, only exact terminal-to-trajectory
suffix reconciliation remains.  Neither finalization path may invoke a worker.

The trajectory is reconciled from durable state rather than appended on blind
best effort.  Its only valid order is capsule prepared, authorization recorded,
authorization consumed, signer 1 complete, signer 2 complete, signer 3
complete, then the complete or invalidated terminal.  On re-entry an already
valid prefix is retained and only its missing suffix is published.  A divergent
row is terminal; a process interruption between state publication and log
publication therefore cannot cause either a repeated key generation or a
permanent gap in the path log.

## Explicit zero surface

Q5A permits exactly three key-generation worker actions and their six OpenSSL
keygen/public-derivation calls.  Certificate-body signing, certificate
signatures, certificate-envelope publication, issuance, Docker, measurement,
target/truth/split/role access, Q1/Q2/Q3 reread, archive access, network,
synthesis, MDL, external scientific claim, adoption, promotion, `ACTIVE`,
production and current-pointer mutation remain zero or false.

## Q6 signature correction

Q4's `FinalCertificateEnvelopeV1` decoder is structural only.  The Q4 body
helper `signature_message` covers the body hash but not the envelope timestamp
or key epoch.  Q5A therefore freezes a future policy identifier for an
envelope-without-signatures preimage that must bind, at minimum, certificate
kind, creation time, current epoch, body hash, pinned genesis root and current
status root.  Q6 must implement and verify that new preimage; successful Q4
structural decoding alone can never be an issuance gate.
