### 仍未充分落实的核心

**第一，调度依据仍偏向对象身份和数量。** v5要求改善“固定条件下研究哪些对象”，分层轮转只是其中一部分。当前新增10对象主要落在两个完整执行合同组，按对象数分摊会让表示为多少份对象影响计算份额。即使已有拟合复用能避免部分重复数值工作，也不能自动消除分配及父稿切换的影响。

不能因此直接把整类删掉或一律合并。共享执行合同不等于来源、支持和适用语义相同；只有确实相同的执行工作才可复用，科学对象和反例仍须保留。

**第二，学习器更清楚“怎样改程序”，还不够清楚“何时值得这样改”。** 当前`propose_revision`要求来源有失配、父模式匹配、当前父稿在声明证据上有失配，再进入绑定和拟合。这些条件必要，但主要表明“可以尝试”，不是哪一种残差支持哪一项结构修订。普通拟合与MSE比较承担了大量后续筛选。

所以，当前并非完全没有结构学习；更准确的是：**有可执行编辑提案，尚未证明这些提案学到了足以改善研究分配的适用条件。** 这与v4的“研究哪个前提”、v5的“反例驱动修订”、v6的“结构修订器”目标仍有距离。

**第三，本轮实验设计能力没有被检验。** 本轮固定97行、不购测，三臂物理实验选择均为0。这是有用的窄消融，能隔离候选修订作用；它不回答系统能否设计区分实验，也不能用更多同类静态seed补出该结论。

## 31. 2026-10-25 底层I/O根因：NOIO上下文中的9p缓冲分配失败

**故障机制已定位，底层存储尚未迁移。** 当前路径为XFS → loop0 → D盘镜像文件 → WSL 9p。历史内核栈直接记录loop工作线程内`p9_fcall_init`的order4内存分配失败；同版本内核源码确认NOIO约束、`ENOMEM → BLK_STS_RESOURCE → 写回AS_EIO → FICLONERANGE返回EIO`的传播路径。[内核因果链与源码定位](</mnt/hegel-snapshot-cow/pr3_io_root_cause_20261025/kernel_io_causal_chain.json>)。

上次未沿用已存的RAW时钟纠正，导致事故时间未对齐；现已补正。本机dmesg应按`CLOCK_MONOTONIC_RAW`换算，不能直接减uptime。写回故障估计为UTC14:09:07.228，原完整20异常记录文件在14:09:08.731新建，相差约1.50秒；应用原栈明确在区间共享ioctl失败，当时Python预算未耗尽。时间、调用链与异常处理流程共同支持同次事故关联；异常后最终快照又成功写成，符合瞬时资源失败的表现。[原异常与时间证据](</mnt/hegel-snapshot-cow/pr3_io_root_cause_20261025/attempt03_application_io_link.json>)。

该故障不能仅归为“没有64KiB连续块”：内核快照仍有1130个这类块；NOIO回收约束、内存水位和保留页会影响可分配性。尚未记录具体分配器拒绝分支、最高占用进程和被删除临时文件的原始inode身份，不能补写这些细节。当前XFS health为尚未收集，成功读写不等于完整健康检查通过。
