# 互补联合知识与作用域撤回收据（0.181.0续研）

本轮把上一轮的“两个来源其实是同一条律”的冗余例子换成真实互补结构：来源 A 是当前项 `0.6*x`，来源 B 是带启动保护的滞后项 `1.2*lag(x,2)`。联合候选不是元数据拼接，而是一个实际可执行的 `add(call_A, call_B)` 程序；两个 call 的定义分别带有 A、B 的来源概念 ID。

运行：

```bash
PYTHONPATH=src python3 scripts/run_source_feedback_complementary_bundle.py
```

同一响应前缀上，空基线损失约 `0.43138`，A-only 损失约 `0.35235`，B-only 损失约 `0.08966`，联合程序损失为 `0`。未见响应上，联合相对 B-only 再降低约 `0.11012`，相对 A-only 再降低约 `0.40535`；因此两个来源各自都提供另一来源无法替代的部分。四个掩码使用同一生成规则和同一执行限制，联合 lineage 的两个 source-local comparison 仍合并为一条 `joint_return`，共享适配和比较成本只计一次。有限样本交互项为 `-0.01945`，原样保留，不把它包装成协同证据；本轮结论依赖两个正的边际贡献和联合优于任一单源。

随后把滞后机制从 `1.2` 改为 `0.45`，联合程序产生可重复的响应失配。`record_transfer_counterexample` 只使联合 `add(call_A, call_B)` 在新目标条件下被 `transfer_refuted`；单独的 A call 和 B call 仍未被判为撤回。这解决了“联合失败误伤可复用子知识”的作用域问题。

这条收据证明了互补程序的价值计算、共享成本去重、联合绑定的局部撤回，以及共享回报不会重排单源报价；但没有证明长期多任务净收益。下一主线仍需把真实连续任务序列接到 source scheduler，验证联合正负回报在多次访问中仍按 canonical binding 分配，并观察投入选择和后继质量的稳定净收益。

续研的作用域回归验证了同一 visit 内的两个替代模板不会互相确认；把库保存为 JSON 后，下一次独立访问的 `transfer` 序号继续递增。2026-10-04 审计发现，写入分开并未保证读取隔离：单源回报匹配仍忽略具体 program，跨访问近零收益也能错误完成确认；非相邻重复程序的合并还会覆盖不同候选。上述三项现已修复并通过交叉路径回归：读取按具体程序匹配，近零收益不提升确认，非相邻重复程序合并回其原位置。新窄链证据见[修复结果](hegel_machine_narrow_cycle_repair_20261004.md)；本篇手工互补来源仍只提供机制证据。
