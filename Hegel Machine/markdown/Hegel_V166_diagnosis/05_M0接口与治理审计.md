# V16.6 M0：执行语义、版本关联、授权与保真压缩审计

固定提交：`675f52612a9d0f1fb208da8bdb0552de3c571758`。读者日期：2026-11-19。本文为主审计的代码专题，不单独评价全部实验效用。

## 1. 判断与证据边界

**本轮确实修好了上一轮数个具体接口问题，但“这些接口分别可用”与“普通研究循环通过这些接口形成、修订并安全复用一个对象”仍需区分。** 问题合同的正常更新路径会提升语义版本、归档、清答案和缓存，并通知直接研究消费者；带有可执行谓词的工作流能根据当前目标观察切换分支；已表示为工具错误的采集失败不会成为一个科学反例；对象依赖中的 AND/OR 删除逻辑有实际效果。这些都不是仅增加字段。

仍有三类证据强度不同的缺口：

1. **原始提交回执直接出现的版本关联问题：** `eval_cluster_01` 的 `ci_mid_bisect` 已为 v2，连接它的 `wh_A_ci_dac_bisect` 仍指向 v1；五个目标回执仍使用此边。这证明边的证据版本与实际节点版本没有闭合，不能据此说五个答案均错误。
2. **真实执行函数上的受控输入缺口：** ordered M1 求解器在授权函数明确拒绝 guidance 时仍执行被召回的路径，并在结果标记使用该 wormhole；没有当前谓词的工作流把来源任务的反驳结果当成新目标结果；FidelityCompression 可把互相冲突的 Acc/Rej 合并成 Rej 并宣告保真。它们是可复现代码行为，不能冒充本次 56 个目标已全部触发。
3. **接口接线及边界缺口：** forest 修订没有传递已有 QuestionSpec；递归展示字段剥离可能误删程序字面值；嵌套 EXECUTION_ERROR 可被 typed-answer 通道接收。这些都有定点控制，但当前 M1 的 25 个 active node 均无 `question_id`，因此不能把它们说成当前实验已发生的语义答案污染。

## 2. 复核方式

输入是固定提交的精确源码与沉积回执。实际执行的文件为：

- `analysis_v166_review/m0/probe_m0_semantics.py`：12 个有目的的离线控制；支持 `--repo` 与 `--output`。
- `analysis_v166_review/m0/m0_semantics_results.json`：控制结果、适用范围、源码 Git blob SHA-1。
- `analysis_v166_review/m0/m0_receipt_review.json`：对原始 JSONL 的只读关联检查，记录异常节点、边、目标与原文件行号。

为绕过包 `__init__` 对无关 formal 模块的急切导入，控制脚本建立 namespace package shim；所审核心函数没有修改。`open_assigned_question` 使用 AST 提取的真实函数，仅调用已有 live-question 更新分支；`step_question` 使用 AST 提取的真实函数并提供明确的 typed query-result 与简单 mission-accounting stub。工作流的采集/拟合使用玩具工具边界。ordered M1 拒绝授权控制使用真实 `HegelV166Researcher.solve_target`、真实授权函数及公开的 ordered toy lab，不 monkeypatch 授权结果。

**这些控制没有调用模型 API，没有完整启动 InquiryLLMAgent，没有重跑完整物理研究，也没有声称独立跑通过整个项目 pytest。** 源码中的原测试已全文阅读，其覆盖范围与我们的增补控制分别说明。

## 4. 原回执直接触发：对象升版后，边继续承载旧版本证据

### 4.1 当前数据中的精确范围

回执目录为 `docs/evidence/v16_6_cross_domain_wormhole_20261119/`：

- `hypothesis_versions.jsonl` 共 42 行，其中 active node 25 个、active wormhole 12 个；25 个 active node 的 `question_id` 全为空。
- `eval_cluster_01`：该文件第 2 行 active `ci_mid_bisect` 为 v2；第 9 行 `wh_A_ci_dac_bisect.node_a_version` 仍为 1。
- `alignment_and_scope_checks.jsonl` 第 1、2、3、5、13 行分别对应 T_A1、T_A2、T_A3、T_A5、T_C3，均使用此边且 authorization 为 granted。
- 另外三个 eval cluster 的 ci 节点仍为 v1，未发现同一错配。不能把一个簇的问题扩展成四簇、20 次 A-wormhole 使用全部失配。

M1 先建立 wormhole，随后在看到 earlier-than-bisect-candidate 的近失配后修订 ci 节点（`cross_domain_arms.py` 604–620、645–679）。边保留先前版本，而 `recall_mid_layer_wormholes` 620–669 直接按 node id 取得当前节点，没有要求其版本与边的 `node_a_version/node_b_version` 一致。`weaker_parents_of` 492–500 同样不核对 local implication 的端点版本。

**影响是证据归属和授权依据变得不精确。** 当前目标还有独立确认与其他 solver 检查，因此这项错配本身不是“答案必错”的证据；它却使“旧边已验证，所以新 claim 可以沿旧边继续复用”的解释无法成立。

### 4.2 问题合同的修订链尚未接通

`empirical_revise_node` 582–618 再调用 `register_node` 时没有传入 `question_spec`。后者 415–426 只有收到该参数才调用 `adopt_question_semantics`，439–440 在缺省时将问题关联记为空。

受控例子从真实有 question 的 a@1 出发，修改 claim 后得到 a@2，但结果为：

- 新节点 `question_id=None`；
- 旧问题仍为 meaning v1，保留旧语义答案；
- 旧 local implication 仍返回 parent，旧 wormhole 仍被召回。

这说明单独正确的 QuestionSpec 升版接口没有自动覆盖 forest 科学修订。**由于本次 M1 节点本来没有 question_id，这一控制不能证明本次产生了旧答案污染；它证明当前 M1 尚未用这套问题语义接线闭合 lifecycle。**

### 4.3 最小修复及验收

修订入口保留稳定 question id，以新 claim/task/readout/protocol 调用已有语义更新函数；若节点本就没有 question，可以明确继续作为无 QuestionSpec 的独立对象，但报告不要将其计为已接入问题循环。所有边继续固定端点版本：升版后标记待重新验证，或回放/重建一条指向新版本的新边；不要仅把版本数字改成最新。

验收只需一个已关联问题、带两类边的对象：合同改变后旧答案失效、直接消费者需重建、旧边不可授予新版本 guidance；重新验证产生新证据后恢复。再在现有 eval01 上核对五个回执引用的具体版本与证据，不要求重写整个图框架。

## 5. M1 授权有消费缺口；四档权限仍部分依赖未绑定布尔值

ordered 分支 `cross_domain_arms.py` 949–964 调用并记录 `authorize_abstraction_use`，随后 966 起直接执行二分，没有依据 `auth.granted` 选择试探或 fallback。该调用的 `heldout_confirmed=True` 也是字面值，并非此目标此 claim 此版本确认回执的查询结果。

控制令 claim 的必要条件为 `reset_protocol_verified=True`，目标没有这个字段。真实授权返回：

```json
{"granted": false, "granted_tier": "bounded_trial", "reason": "unknown_precondition_requires_probe_before_guidance"}
```

真实 solver 仍完成目标、返回 boundary 7，并报告 `used_wormhole="blocked_wh"`。这里的答案碰巧正确；证明的是权限决定没有成为执行边界，不能用“最终有确认”来替代“授权拒绝后到底执行了什么”的核对。现有 ordered 回执未出现这一拒绝输入，故这是**真实 M1 路径的受控触发**。

授权 API 本身还有相关边界：`wormhole_forest.py` 175–193 只拦截为 TRUE 的 exclusion，255–261 仅处理 UNKNOWN preconditions；UNKNOWN exclusion 不降档。274 起可仅凭 `heldout_confirmed`、`implication_verified` 和 supported 字段授予 validated_pruning。控制中 claim 与 edge 都声明 retrieve_candidate、exclusion 的所需特征缺失，两个调用布尔值置真后仍得到 validated_pruning。应明确这些声明是最大能力、当前状态还是仅展示字段，并在执行代码中落实同一解释；不能把调用者传入的两个真值等同于已核验的版本/范围证明。

也应给现有实现准确 credit：一维尾部路径 1153–1181 会先实际测 heldout residual，再检查授权并独立确认；原回执 B5、部分 B4 确实记录 exclusion 拒绝。问题不是“整个系统的授权全是日志”。尺度路径 1082–1098 则只对一个拒绝 reason 作 fallback，其余拒绝原因仍须统一消费。

最小修复：把授权返回值作为执行 switch；retrieve 只能召回，bounded_trial 走显式限额诊断，guidance 才执行复用，pruning 还需绑定 implication evidence。证据至少绑定 target/claim/node version/protocol；缺失的 exclusion 特征触发有限诊断或 UNKNOWN，不能直接剪枝。验收包括上述 unknown 条件、已知不满足条件、独立确认失败、证据属于旧版本四例。先修实际消费者，不必先增加权限枚举。

## 6. 工作流回放：有谓词时已修，无谓词时仍继承来源结论

编译器把历史结果写入 `observed_outcome_status`（`growth_methods.py` 137–138）。回放 `_evaluate_condition_node` 会计算已支持的 diagnostic/residual/gap 谓词；但没有或无法识别当前谓词时，`workflow_execution.py` 52–53 直接返回历史 `observed_outcome_status`。

同一来源例子为 REFUTED 的工作流，在有当前 diagnostic predicate 时正确得出 SUPPORTED，跳过反驳支线，只执行 step0 acquisition；去掉 predicate 后，回放把来源 REFUTED 当成当前结果，并真的执行 step2 acquisition。控制比较的是实际购买分支探针的变化，超过了一个状态字段的断言。

**缺的是“这个目标为什么满足该分支条件”的当前证据。** 允许历史 witness 作为来源、解释、候选诊断，不应把它直接用作新目标的 outcome。无谓词时应返回 UNKNOWN，或将需要新证据的判别节点加入 frontier，不能凭来源标签开启 REFUTED 分支。未知 predicate kind 同样处理。

验收采用同一历史反驳例子，加两个新目标（支持与反驳）和一个无可执行谓词版本：前两者按新测量分流，第三者停在未知/诊断；工具错误不变成 UNKNOWN 下的反驳捷径。M1 `cross_domain_arms.py` 没有调用此工作流编译/回放系统，因此本条是核心 API 缺口，不能拿它解释本次 M1 的测量收益。

## 7. FidelityCompression 还不能宣称完整保持 Acc/Rej/Unknown

`wormhole_forest.py` 320–365 的合并器以 A 为基底构造 merged，评价三个 verdict，阻止新增 REJ 与部分丢失接受；但 348 仅在源 A/B **均不是 REJ** 时统计丢失 ACC。

实际 evaluator 控制：同一 query 下 A 预测 False、B 预测 True、观察 True，因此源集合为 `{REJ, ACC}`；merged 取 A 后为 REJ，函数仍返回 accepted=True。另一显式 verdict-table 控制给出 A/B 都 UNKNOWN、merged ACC，也 accepted=True。后一个控制仅证明验收谓词未禁止未知升级，不宣称当前 merge 生成器自然发现了这个新知识。

对矛盾证据选择 REJ 可以是一种后续科学裁决，但裁决需要范围划分、证据可靠性或额外判别；它不是仅压缩表示就“保留全部区分”。UNKNOWN→ACC 也可能在新验证后成立，但这属于知识增长。

最小修复无需通用定理器：在冻结 witness query 集上比较按 scope/协议归一的 verdict。来源冲突则拒绝纯合并，或产生保留两个条件分支的对象；UNKNOWN 不在纯压缩步骤自动升为 ACC/REJ。新增科学证据进入独立 revision event。验收加入 `{ACC,REJ}`、`{UNKNOWN,UNKNOWN}→ACC`，保留现有 false-new-REJ 测试；输出保真评估的具体 query id、来源版本和 verdict，而非仅空损失列表。

## 8. 两个小而确定的边界：建议随上述修复处理

### 8.1 展示字段剥离应识别 schema 位置

`question_semantics.py` 40–45 对所有嵌套字典递归删除 notes 等键。predicate 的 `value={"notes":"mode_A"}` 改为 mode_B 时，真实 predicate 对同一目标的判定从 TRUE 变 FALSE，但 digest 未变，旧答案保留。`notes` 在这里是程序字面值的一部分，不是 UI 元数据。

保留对合同结构内展示注释的递归处理，给 opaque literal/payload/expression value 设置明确边界，或将展示字段放到专门 metadata 容器。验收一对普通 display_label 改名与一对上述 literal 改值即可。当前目标没有显示触发该边界。

### 8.2 EXECUTION_ERROR 的顶层/值层表示不一致

`question_continuation.py` 595–599 检查 top-level `answer.outcome_status`，而 scoped_outcome 类型验证在 `question_semantics.py` 193–195 检查 `answer.value.outcome_status`。给真实 step_question 一个 `status=answered, value.outcome_status=EXECUTION_ERROR` 的 typed result 时，它保存 semantic_answer，并返回 answer_ready_no_parent_use。

本控制提供了 query-result stub，没有证明普通 query engine 会产生这个形状，也没有产生 parent-use。修复为单一规范化 outcome 提取函数，先判 execution error，再验证是否为知识答案；补足 nested/top-level 两种输入的兼容测试即可。

## 9. 对“100% 通过”和下一步施工的准确解释

原 M0 测试是有价值的回归测试，但通过它们只支持其已覆盖输入：正常合同字段改动、有 predicate 的分支、一个已知 exclusion、选定数学例子、AND/OR 删除，以及无冲突的保真损失。它们尚未覆盖上述版本关联、无谓词回放、拒绝授权的实际消费者和矛盾 verdict。报告应把“测试集通过”与“全部执行合同闭合”分开。

本轮最小施工顺序：

1. **先补 M1 执行边界和端点版本消费。** 修拒绝后仍复用，修已修订节点的旧边证据；用现有 eval01 验证关联恢复。
2. **补回放条件真实性。** 无当前判别程序就 UNKNOWN/诊断；明确来源 witness 只提供候选与出处。
3. **补保真压缩的冲突/未知门。** 科学修订和等价压缩分别记账。
4. **接一次小而完整的 QuestionSpec 主线。** 一条普通研究产生的对象，经过真实修订，更新问题含义、清旧答案、使旧边失效，再形成有效新边并在未见目标复用。不要只用新的独立测试代替接线。

展示字段 literal 与 error 表示可作为这四项的同批小修。无需再建立一套新的大框架。效用实验的成败仍应由冻结目标、强普通方法、实际测量成本与正确性共同决定；本专题不能替代其他审计对收益、生成自主性、强基线和严格 earliest 合同的判断。
